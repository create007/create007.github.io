2. Linux C Demo 实现

libheif 的设计初衷是编解码库（Image Codec Wrapper），其核心工作流是 Decode -> Pixels -> Encode。它并没有公开的 API 直接支持 “Muxing”（将现有的 H.265 码流直接封装而不重新编码）。

如果您手头已经有 H.265 I 帧（bitstream），想要封装成 HEIF，通常有两种路径：

  1. 标准路径（推荐 Demo）：先解码为像素，再编码为 HEIF。这保证了兼容性，但会有重编码的性能开销。
  2. 高级路径（透传插件）：编写自定义 heif_encoder_plugin，欺骗 libheif 直接写入您的 NAL 数据。这非常复杂（涉及手动解析 NAL），不适合作为基础 Demo。

这里提供标准路径的 C 语言实现：demo_heif.c。它展示了如何读取一个图像（或 H.265 帧，如果使用 libde265 解码），将其加载到 heif_image 中，然后使用 heif_encoder 封装输出。

已为您修复了 Segmentation fault 问题。

问题原因

在 demo_heif.c 中，当从裸流 H.265 转换为 heif_image 时，我只调用了 heif_image_add_plane 为 Y 分量分配了内存，遗漏了 Cb 和 Cr 分量的内存分配。导致后续 memcpy 复制色度数据时访问了空指针，从而触发段错误。

修复内容

我在 decode_h265_bitstream 函数中补充了 Cb 和 Cr 分量的平面添加逻辑，并根据色度采样格式（4:2:0, 4:2:2, 4:4:4）正确计算了色度平面的宽高。

  • Main brand: heic: 说明这是标准的 HEVC (H.265) 编码的 HEIF 图像。
  • Compatible brands: mif1 (HEIF通用品牌), miaf (Multi-Image Application Format) 都是标准的兼容标识。
  • 结论: ✅ 文件头正确。

2. 图像基本信息 (Image Properties)

  • 解读:
    • 3840x2160: 分辨率是 4K，与您输入的 H.265 I 帧源分辨率一致。
    • primary: 标记为主图像（HEIF 文件可以包含多张图，必须有一张是主图）。
  • 结论: ✅ 分辨率和主图标记正确。

3. 颜色与编码信息 (Color & Coding)

  • 解读:
    • colorspace: YCbCr, 4:2:0: 使用了标准的 YUV 4:2:0 采样，这是最通用的 H.265 编码格式。我们在代码中正确设置了 heif_image_add_plane 来处理 Y, Cb, Cr 三个分量。
